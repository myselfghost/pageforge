## 2. 场景 1：HTML/CSS/JS 缓存命中 QPS

缓存全部命中（预热后压测），同一对象反复请求：

| 用例 | 并发 | QPS | p50 | p99 | 吞吐 |
| --- | --- | --- | --- | --- | --- |
| index.html（约 240 B） | 100 | 11,449 | 7.95 ms | 25.2 ms | 3 MB/s |
| app.js（149 KB） | 100 | 5,181 | 10.5 ms | 156.6 ms | 776 MB/s |
| style.css（54 KB） | 100 | 7,938 | 3.4 ms | 111.9 ms | 434 MB/s |
| html/css/js 混合（200 并发） | 200 | 8,504 | 22.3 ms | 47.5 ms | 202 MB/s |
| 混合（500 并发） | 500 | 8,853 | 54.1 ms | 108.1 ms | 140 MB/s |
| 混合 5 分钟长稳压测 | 100 | 8,509 | 10.6 ms | 51.1 ms | 234 MB/s |

关键结论：

1. 小文件场景 QPS 上限约 **1.1 万/秒**；1MB 级对象吞吐可达 **1.4 GB/s**。并发从 200 提到 500，QPS 仅从 8.5k 升到 8.9k，**已到服务端 CPU 瓶颈**。
2. 服务端 CPU 在 8.5k QPS 时约 **440%–519%（4.4–5.2 个核，占整机 37%–43%）**，平均每请求约 0.5 ms CPU；剩余瓶颈来自 Go HTTP 栈与逐请求日志。
3. 每次缓存命中仍发生 **约 1.5 次磁盘读操作**（25.9k IOPS 对应 8.5k QPS），即缓存对象未常驻内存，依赖 OS 页缓存。
4. 5 分钟长稳：**0 个非 200 响应**，QPS 每秒区间 8.1k–10.5k（±15%），无内存增长：caddy 工作集 64→70 MB、私有内存 87→92 MB、句柄 1020–1144、线程 111–117。
5. 冷启动单对象首次回源延迟约 **15–21 ms**（1MB 级对象，MinIO 本地）。

## 3. 场景 2：MinIO 不可用（进程停止）

| 请求类型 | 结果 |
| --- | --- |
| 已缓存对象 | 9,669 QPS 正常返回 200，p50 9.4 ms —— **完全不受影响** |
| 未缓存对象 / 未缓存清单分片 | **502**，平均 3.78 s、p99 5.5 s、最大 5.6 s |
| 50 并发全部击穿缓存 | 失败吞吐仅 14 req/s（每个请求串行等待 SDK 重试退避） |
| MinIO 恢复后 | 首次未命中请求 15–21 ms 恢复成功，无需重启代理 |

- 代理进程不崩溃、健康检查正常；缓存隔离性好。
- 问题：**没有快速失败**。MinIO 拒绝连接时，S3 SDK 默认重试（约 3 次退避）导致每个未命中请求耗 3.8–5.6 s，客户端表现为“长时间挂起后 502”。建议加熔断/更短超时，使未命中在 1 s 内快速 502。
- 错误日志按每次尝试记录 `stat … connection refused`（同一请求出现 2–3 条重复），可作为噪声来源之一。

## 4. 场景 3：Control 停止与重启

| 检查项 | 结果 |
| --- | --- |
| 停止 control 后已缓存+未缓存请求 | 9,806 QPS、p50 9.9 ms、p99 25.7 ms，**全部 200**（快照在代理内存中，对象直接从 MinIO 取） |
| 未知域名/路径 | 404（沿用最后快照） |
| `/__pageforge/healthz`、`/readyz` | 均 200 —— **readyz 不反映快照陈旧度** |
| 代理错误日志 | 每 2 s 一条 `snapshot poll failed`（约 30 条/分钟，warn 级） |
| 重启 control 后 | 约 2 s 内快照刷新；新建绑定 4 s 内生效；错误日志不再新增 |

补充观察（异常事件）：测试期间出现过一次 **control 约 153 秒无响应**：期间代理快照轮询超时，新启动的代理实例因快照代数=0 对所有请求返回 **503**；control 自行恢复后无需重启即正常。该实例当时以“无 stdout 重定向”方式启动，SQLite 侧 `MaxOpenConns=1`，存在“日志写入阻塞或单连接被长查询占用”两种可能；改用重定向启动后做 5 分钟持续压测（154 次探测，最大延迟 318 ms）**未复现**。建议后续专项排查，并为快照轮询增加“沿用本地磁盘快照”的兜底。

## 5. 场景 4：缓存上限 10 MB、工作集 64 MB（独立实例 :8090）

使用 64 个 1 MB 对象（共 64 MB）随机请求，LRU 上限 10 MB：

| 用例 | 并发 | QPS | p50 | p99 | 错误 |
| --- | --- | --- | --- | --- | --- |
| 基线（1 GB 缓存、全热） | 20 | 1,485 | 12.0 ms | 34.0 ms | 0 |
| 基线（1 GB 缓存、全热） | 100 | 1,431 | 54.1 ms | 262.4 ms | 0 |
| **10 MB 缓存** | 20 | **195** | 105.5 ms | 205.3 ms | **5.3% 502** |
| **10 MB 缓存** | 100 | **325** | 320.5 ms | 597.5 ms | **32.4% 502** |

结论与问题：

1. 命中率按容量/工作集估算约 **15%**（10 MB / 64 MB），QPS 相对基线下降 **4.4–7.6 倍**，延迟上升 3–9 倍，属于缓存抖动（thrash）的预期表现。
2. **缓存目录实际占用突破上限**：峰值观测到 **49 MB（约 10 MB 上限的 4.9 倍）**，压测结束后仍残留 **15 MB**。原因是 Windows 上对被读取中的文件执行删除会失败，代码忽略删除错误，条目已从索引移除但文件残留，且不会再次回收。
3. **并发击穿同一对象时产生 502**：错误日志中 **3,593 条 `cache entry disappeared`**。单飞（singleflight）跟随者在等待期间，条目已被容量淘汰，随后查不到条目直接报错返回 502，而不是回源重试。
4. 建议：删除失败进入延迟回收队列（或改用句柄可删除的打开方式）；跟随者查不到条目时改为重新加载/直接回源；缓存上限按“含在途写入”统计，避免瞬时大幅超限。

## 6. 场景 5：单包 10 万文件并发访问

| 用例 | 并发 | QPS | p50 | p99 | 错误 |
| --- | --- | --- | --- | --- | --- |
| 冷启动（清单分片懒加载，500 个随机文件/约 100 分片） | 100 | 11,449 | 8.1 ms | 17.1 ms | 0 |
| 全热（清单已在内存） | 100 | 12,655 | 7.4 ms | 16.0 ms | 0 |

- 发布 10 万文件包（zip 100k 条目）耗时 **236.5 秒（约 423 个对象/秒，workers=32）**，功能正确但发布吞吐偏低。
- 清单内存占用：冷加载后 caddy 工作集 64→141 MB、私有内存 92→164 MB；再次全热压测后**不再增长**，无泄漏。

- 10 万文件不影响在线请求的 QPS 与延迟，10 万级包可正常服务。

## 11. 场景 7：1 万 Project / 2 万 Binding 路由性能（纯基准）

> 直接对 [internal/router/router.go](file:///e:/soft/rdesk1.5/internal/router/router.go) 跑 Go benchmark，不依赖 control/proxy/minio 进程。
> 实测覆盖 4 种配置形态：真实生产通常是"少量 host + 大量 path 前缀"，极端形态是"全 wildcard host"。

### 11.1 测试代码

基准文件：[internal/router/router_bench_test.go](file:///e:/soft/rdesk1.5/internal/router/router_bench_test.go)

```powershell
go test ./internal/router -bench=. -benchmem -benchtime=1s -run=^$
```

### 11.2 Match 单次路由查找耗时

| 配置 | 每次耗时 | 单核 QPS | 内存分配 |
| --- | --- | --- | --- |
| 2 万 binding 挂在**同一 exact host** 的不同 path 上（Trie） | **38.9 ns** | **~2,570 万** | 52 B/op · 2 次 |
| 2 万 binding 挂在**2 万个不同 exact host**（map O(1)） | **23.2 ns** | **~4,310 万** | 16 B/op · 1 次 |
| **真实形态**：100 个 exact host × 100 个 path = 1 万 binding | **49.5 ns** | **~2,020 万** | 48 B/op · 2 次 |
| 2 万 binding 挂在**2 万个不同 wildcard host**（线性扫） | **4,060 ns** | **~24.6 万** | 16 B/op · 1 次 |
| 上一个配置，请求全**不命中**（扫完 2 万条落到 fallback） | **15,516 ns** | **~64.5 万** | 0 B/op · 0 次 |

**结论**：只要不是"全 wildcard"这种极端配置，**2 万 binding 路由查找仍是 ns 级**，对端到端 QPS 完全无感知（之前 proxy 在 8.5k QPS 时瓶颈是 CPU/日志/IO，路由仅占 0.1% 以下）。wildcard 线性扫是已知设计，O(N)；但 wildcard 全 miss 反而**省分配**。

### 11.3 Build（构建路由表）耗时

`Build` 是每次快照刷新时执行的，属于低频操作。

| 配置 | 耗时 | 内存 | 分配次数 |
| --- | --- | --- | --- |
| 2 万 binding 单 host（Trie 构建） | **5.5 ms** | 5.9 MB | 80,151 |
| 2 万 binding 2 万 exact host（map 构建） | **7.1 ms** | 5.7 MB | 80,147 |
| 1 万 binding 真实形态（100 host × 100 path） | **4.0 ms** | 2.8 MB | 41,312 |
| 2 万 binding 2 万 wildcard host | **3,391 ms** ⚠️ | 8.2 MB | 140,021 |

⚠️ **发现 Build 端的 O(N² log N) 问题**：wildcard 配置下，[router.go:62-74](file:///e:/soft/rdesk1.5/internal/router/router.go#L62-L74) 的 `host()` 函数在每次添加新 wildcard 时都会先线性扫（O(N)）查重，然后 `append` 后对整个 slice `sort.SliceStable`（O(N log N)）。N 次新 wildcard → **O(N² log N)**。2 万 wildcard 时 Build 要 3.4 秒，而同等规模的 exact host 只需 7 ms。

真实生产不会有 2 万个不同的 wildcard host（通配符通常也就几个），所以**不影响**正常场景；但如果有人配置了大量不同的 wildcard host（比如 `*.a1.example.com`、`*.a2.example.com` ...），刷新一次快照会卡 3 秒以上。

### 11.4 建议

| 优先级 | 问题 | 修复方向 |
| --- | --- | --- |
| P1 | Build wildcard 的 O(N² log N) | 1）在 exact map 之外再加一个 `wildcardMap` 做 O(1) 查重；2）先全部 append 完再一次性 sort；3）单次 Build 结束后再排序，而不是每次 append 都 sort |
| P3 | Match wildcard 的 O(N) 线性扫 | 如果 wildcard 规则数可能上千以上，可改为按 suffix 长度分桶或 Trie（当前 wildcard 通常 <10 条，O(N) 成本可忽略） |

修复后 Build wildcard 的复杂度可降到 **O(N log N)**（一次性 sort），预计 2 万 wildcard 从 3.4 s 降到 70 ms 以内；Match 侧保持不变。
